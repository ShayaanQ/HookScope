# Milestone 2 — Outbound Delivery and Secure Replay

## Objective

M2 adds operator-configured outbound destinations, one immediate outbound HTTP delivery attempt after successful durable webhook ingestion, persisted delivery/attempt observability, and secure replay of a stored event to an existing destination. Durable capture remains the primary success condition: downstream delivery never determines the incoming webhook response.

M2 is intentionally not the reliable-queue milestone. A process crash may occur after event persistence but before delivery creation, during delivery, or before final delivery-state persistence; M2 does not recover those cases. M3 owns Redis, Redis Streams, workers, retries, backoff, crash/pending recovery, DLQ, and durable queued-delivery semantics.

## Checkpoints

### M2-A — Destination foundation and outbound security boundary

Destination persistence, create/get/list APIs, endpoint ownership, URL validation, exact operator allowlist, privacy/error contracts, and schema/API tests. No delivery execution.

### M2-B — Single-attempt outbound delivery

Delivery and attempt persistence, outbound HTTP client, post-ingestion integration, exactly one initial attempt, success/failure recording, query APIs, and failure isolation. No replay.

### M2-C — Secure replay

Authorized replay to an existing destination belonging to the event’s endpoint, persisted-event reuse, auditable `REPLAY` delivery, exactly one replay attempt, and query/privacy/error coverage.

### M2-D — Hardening and release verification

Migration/schema/index, outbound-security, privacy/logging, architecture/ADR, manual, clean-checkout, Gradle, CI, and complete evidence reviews.

## Locked contract

### Destinations

`webhook_destinations` has UUID `id`, required `endpoint_id`, required `url` TEXT, and UTC `created_at` (`timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP`). The foreign key is `NO ACTION`; a destination belongs to exactly one endpoint. Exact duplicate URLs are forbidden per endpoint. Update/delete are out of scope.

Management remains protected by the M1 admin token:

- `POST /api/v1/endpoints/{endpointId}/destinations`
- `GET /api/v1/endpoints/{endpointId}/destinations`
- `GET /api/v1/endpoints/{endpointId}/destinations/{destinationId}`

Creation accepts `{ "url": "https://receiver.example.com/webhooks" }`. Existing M1 response, pagination, ordering, Problem Details, and privacy conventions apply.

### Outbound host boundary

Configuration is `hookscope.delivery.allowed-hosts`, a collection of exact hostnames/IP literals. An empty collection is valid and denies every destination creation. Hostname/IP authorization uses the parsed URL host and does not resolve DNS for authorization: DNS names compare case-insensitively, IP literals match explicit parsed host values, and alternate DNS targets are not separately allowlisted. There is no suffix or wildcard matching, and wildcard syntax in an allowlist entry authorizes nothing. URL ports do not change host matching. URLs must be absolute `http`/`https`, have a host, no userinfo or fragment, and a valid port. Destination creation compares the parsed URL host to an explicit entry. HTTPS is strongly recommended. Redirects are disabled, so redirects cannot change the destination host. DNS-rebinding protection, custom routing, proxy support, network-level isolation, and network sandboxing are outside M2.

The destination URL may contain its own query component, which remains part of the stored target URL. It is ordinary operator configuration, not a secret-storage mechanism; operators must not put credentials or secrets in it. Userinfo remains forbidden and M2 has no destination-secret or custom-authentication model. The authenticated management API necessarily stores and returns the configured URL. Logs and Problem Details must not emit a complete destination URL or query string, and outbound logs must not expose URL queries, bodies, captured sensitive headers, or the admin token.

### Delivery persistence

`webhook_deliveries`: UUID `id`, required `event_id`, required `destination_id`, `kind` (`INITIAL|REPLAY`), `status` (`PENDING|SUCCEEDED|FAILED`), UTC `created_at` default, nullable `completed_at`; both foreign keys are `NO ACTION`.

`webhook_delivery_attempts`: UUID `id`, required `delivery_id`, `attempt_number >= 1`, required start/completion timestamps, `outcome` (`SUCCEEDED|FAILED`), nullable valid HTTP status, nullable stable `error_code`, nonnegative `duration_ms`, and unique `(delivery_id, attempt_number)`. M2 creates only attempt 1; M3 may add later attempts.

### Initial delivery and synchronous execution

Initial delivery is synchronous on the ingestion request path after durable event commit. There is no task executor, background handoff, scheduler, queue, worker, or fire-and-forget delivery. M1 validation runs, the event is committed, M2 delivery work runs synchronously, all configured destination attempts finish or fail, and HookScope returns the existing M1 success response. M2 latency therefore grows with destination count and outbound timeout duration; M3's queued workers remove this tradeoff.

For each destination: (A) persist and COMMIT the event first; (B) create a PENDING logical `INITIAL` delivery and COMMIT it; (C) perform outbound I/O with no database transaction held open; (D) transactionally persist attempt evidence and terminal delivery state. A post-event delivery failure cannot roll back the event or convert the incoming response into a delivery failure. A crash before delivery creation may leave no delivery; a crash after PENDING commit may leave PENDING. M2 performs no recovery.

Destinations may be sequential; one failure must not prevent others. Exactly one attempt occurs per initial delivery. No database transaction spans network I/O.

Use the persisted method, exact raw body, and stored destination URL. Do not append inbound query parameters. Use the event's dedicated persisted content-type field: when non-null, send it as the single outbound `Content-Type` value; do not reconstruct it from the captured inbound header collection. Add `X-HookScope-Event-Id`, `X-HookScope-Delivery-Id`, and `X-HookScope-Delivery-Kind`. HookScope must never copy or propagate captured inbound Authorization, Cookie, Host, Content-Length, Transfer-Encoding, Connection, hop-by-hop, Forwarded, X-Forwarded-*, arbitrary provider headers, or captured Content-Type collection values. The HTTP client/protocol stack may generate transport-required headers such as Host, Content-Length, or Transfer-Encoding; those generated values are not forwarding captured inbound values. M2 has no operator-configurable custom destination authentication or custom destination headers.

HTTP policy: never follow redirects; 2-second connection timeout; 5-second overall timeout; normal TLS verification; discard response body/headers. 2xx succeeds; other statuses fail and record status. Transport failures use stable categories `TIMEOUT`, `CONNECT_ERROR`, `TLS_ERROR`, `IO_ERROR`, `INTERRUPTED`, or `UNEXPECTED_ERROR` without raw exception text/stack traces.

Delivery records never persist outbound bodies/headers, response bodies/headers, admin tokens, or full sensitive inbound values. Logs preserve the M1 privacy boundary.

### Delivery APIs

Protected routes:

- `GET /api/v1/events/{eventId}/deliveries`
- `GET /api/v1/deliveries/{deliveryId}`

Lists use deterministic M1 pagination. Representations expose IDs, kind/status, timestamps, and attempt count; detail may expose attempt number/outcome/status/error code/timestamps/duration, never body or headers.

### Replay

Protected `POST /api/v1/events/{eventId}/replay` accepts only `{ "destinationId": "<uuid>" }`. The event and destination must exist, and the destination must belong to the event’s endpoint. No URL, method, body, or header override is accepted. Replay is synchronous: validate, create and COMMIT PENDING `REPLAY`, perform one attempt with no transaction held, persist terminal evidence transactionally, and return `201` with the terminal delivery representation regardless of downstream result. No background replay; the stored event is unchanged.

Delivery invariants are mandatory: PENDING has `completed_at IS NULL`; SUCCEEDED/FAILED has `completed_at IS NOT NULL`. A SUCCEEDED attempt has HTTP 200–299 and null error code. HTTP-response FAILED has status 100–599 outside 200–299 and null error code. Transport FAILED has null status and exactly one of `TIMEOUT`, `CONNECT_ERROR`, `TLS_ERROR`, `IO_ERROR`, `INTERRUPTED`, `UNEXPECTED_ERROR`. Attempts require `attempt_number >= 1`, `duration_ms >= 0`, `completed_at >= started_at`, and unique `(delivery_id, attempt_number)`. M2 creates only attempt 1; database/application invariants prevent contradictory states.

Destination lists order by `created_at DESC, id DESC`; delivery lists by `created_at DESC, id DESC`; attempt details by `attempt_number ASC`. M2 uses the exact M1 pagination envelope, defaults, limits, validation, and Problem Details. Required indexes are UNIQUE `(endpoint_id, url)` and `(endpoint_id, created_at DESC, id DESC)` on destinations, `(event_id, created_at DESC, id DESC)` on deliveries, and UNIQUE `(delivery_id, attempt_number)` on attempts; no speculative indexes are required.

## M1 compatibility

M2 preserves endpoint management, admin-token protection, public ingestion and unknown-key/method behavior, exact bounded raw-body persistence, redaction, query/header representations, direct peer IP, forwarding-header rejection, Problem Details, pagination/order, public health, logging/privacy, Flyway ownership, Hibernate validation, and Compose health. M1 tests remain mandatory.

## Explicit non-goals

M2 does not implement Redis, Redis Streams, queues, workers, asynchronous durable delivery, retries, exponential backoff, worker or pending-entry recovery, DLQ, automatic/scheduled/bulk replay, destination update/delete, operator-configurable custom destination authentication, operator-configurable/custom destination headers, stored destination secrets, inbound signatures/handshakes, real accounts/authentication, multi-tenancy, UI, CLI, SSE/WebSockets, trusted proxies, or retention automation.

Logical deliveries are separate from attempts so M3 can add Redis-backed retry attempts without replacing the M2 domain. M3 stream/message contracts are intentionally unspecified here.

## Testing and release requirements

M2-A covers fresh migrations/schema, destination create/get/list, ownership, duplicates, URL/allowlist validation, auth, Problem Details, and privacy. M2-B covers exact method/body/header policy, metadata, redirect/timeouts/status/transport outcomes, transaction ordering, isolation, one-attempt behavior, query APIs, pagination, and privacy. M2-C covers authorization, event/destination ownership, no arbitrary target, persisted-event reuse, audit metadata, one-attempt outcomes, APIs, Problem Details, and privacy. M2-D requires the independently enumerated release gates in `docs/acceptance/M2.md`, including schema/index/security/privacy/ADR review, all M1/M2 tests, authoritative Gradle commands, clean checkout, Compose, three manual flows, CI, and complete human-owned evidence mapping.

M2-D requires ADR coverage of four decision areas: (1) the destination outbound-security boundary (parsed-host allowlist, URL validation, redirects, DNS/network limitations); (2) synchronous single-attempt delivery and transaction boundaries; (3) the logical-delivery/attempt and replay domain model; and (4) outbound HTTP/privacy policy, including method/body and dedicated Content-Type sourcing, captured-header non-forwarding versus client-generated transport headers, timeouts, redirect/TLS policy, response-data non-persistence, and sanitized error categories. Closely related subjects may share an ADR, but all four areas must be traceable.

M2 production topology remains HookScope plus PostgreSQL. A disposable HTTP receiver may be used only as Testcontainers, a Compose verification profile, or equivalent documented test/release infrastructure for delivery and replay verification. It is not a HookScope production dependency. The chosen mechanism must be documented, and clean-checkout Compose health must not depend on an undocumented external service.
