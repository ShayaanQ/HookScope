# Milestone 1 — HookScope Backend Foundation and Ingestion

## Project purpose

HookScope is a self-hosted webhook inspection and reliability platform. It gives
developers a generated endpoint, preserves what an external sender transmitted, and
provides a management API for inspection. Later milestones add delivery, replay,
retries, dead-letter handling, live updates, real accounts, and a user interface.

## Milestone objective

Prove one durable, well-tested backend vertical slice:

> An operator can create a webhook endpoint, receive an HTTP request at its generated
> public path, persist the request safely and exactly within configured limits, and
> retrieve it through a protected management API.

Sensitive headers are redacted before persistence. Oversized payloads are rejected
without creating partial event records and without buffering unbounded input.

M1 is backend-only. It deliberately excludes UI, live streaming, outbound delivery,
retries, and real user authentication.

## Definition of the user-visible slice

M1 is functionally complete when all of the following work together:

1. An operator calls the management API with the temporary admin token and creates an
   endpoint.
2. The response contains an internal endpoint ID, public key, and relative ingestion
   path.
3. An external sender calls `/hooks/{publicKey}` using a supported HTTP method.
4. HookScope applies bounded body reading, redacts configured sensitive headers before
   persistence, calculates body metadata, and durably stores the event.
5. The external sender receives `204 No Content` only after persistence succeeds.
6. The operator retrieves endpoint and event data through paginated management APIs.
7. Errors use the locked Problem Details contract.
8. After documented environment setup, `docker compose up --build` starts PostgreSQL
   and HookScope, and the public health endpoint succeeds.
9. The authoritative verification command and CI both pass.

## Locked platform versions

M1 uses these pinned foundations:

- Java 21 toolchain
- Spring Boot 3.5.16
- Gradle Wrapper 8.14.5 with Kotlin DSL
- PostgreSQL 17.10 container image, pinned as `postgres:17.10` or to its immutable digest

Dependency patch versions managed by Spring Boot may follow its dependency-management
BOM. All explicitly declared plugins and container images must be pinned; do not use
`latest` tags.

Changing a locked platform version requires explicit human approval and a documented
reason.

## Locked package and module shape

- configuration,

- ingestion/events,
- shared API error handling,
- and persistence/migrations.

Do not create microservices, separate deployable workers, or speculative abstractions.

## Locked API contract

### Temporary management protection

All `/api/v1/**` routes require:

```text
X-HookScope-Admin-Token: <configured token>
```

Public exceptions:

- `/hooks/**`
- `/actuator/health`

The management token contract begins in M1-B.

### Management endpoints

- `POST /api/v1/endpoints`
- `GET /api/v1/endpoints`
- `GET /api/v1/endpoints/{endpointId}`
- `GET /api/v1/endpoints/{endpointId}/events`
- `GET /api/v1/endpoints/{endpointId}/events/{eventId}`

No update or delete APIs exist in M1.

### Public ingestion endpoint

```text
/hooks/{publicKey}
```

Application-supported methods:

- `GET`
- `POST`
- `PUT`
- `PATCH`
- `DELETE`

Application behavior:

- durable persistence succeeds: `204 No Content`
- unknown public key: `404` Problem Detail with `ENDPOINT_NOT_FOUND`
- body exceeds configured limit: `413` Problem Detail with `PAYLOAD_TOO_LARGE`
- `HEAD` or `OPTIONS`: `405` Problem Detail with `METHOD_NOT_ALLOWED`
- the sender never receives internal event IDs, stored request data, or endpoint metadata

`TRACE` is disabled at the server/container level. `CONNECT`, malformed methods, and
other requests rejected before Spring handles them are not guaranteed to use the
application Problem Detail format.

Known future consideration: some providers require handshake-specific `200` responses
or echoed challenge bodies. M1 intentionally remains provider-agnostic.

## Locked response schemas

Field names below are JSON names.

### Create-endpoint request

```json
{
  "name": "Payments sandbox"
}
```

Validation:

- required,
- trimmed before persistence,
- 1–120 characters after trimming,
- blank or longer than 120 characters: `400 VALIDATION_ERROR`.

### Endpoint response

```text
id
name
publicKey
ingestionPath
createdAt
```

`ingestionPath` is relative and equals `/hooks/{publicKey}`.

### Paginated endpoint response

```text
page
size
totalElements
totalPages
content[]
```

Each content item is an endpoint response.

### Event-list item

```text
id
method
path
contentType
bodySize
sourceIp
receivedAt
```

Event lists do not include full bodies, body hashes, headers, or query-parameter maps.

### Event-detail response

```text
id
method
path
contentType
bodySize
sourceIp
receivedAt
headers
queryParameters
bodyBase64
bodySha256
```

`bodySha256` is lowercase hexadecimal. `bodyBase64` is standard Base64 encoding of the
exact stored bytes.

## Locked pagination behavior

Applies to endpoint and event lists:

- zero-based `page`
- default `page=0`
- default `size=20`
- maximum `size=100`
- negative page: `400 VALIDATION_ERROR`
- size less than 1: `400 VALIDATION_ERROR`
- size above 100: `400 VALIDATION_ERROR`
- response fields: `page`, `size`, `totalElements`, `totalPages`, `content`

Ordering:

- endpoints: `created_at DESC, id DESC`
- events: `received_at DESC, id DESC`

The ID tie-breaker is mandatory so ordering remains deterministic when timestamps are
equal.

## Locked Problem Details contract

All application-generated errors use:

```text
Content-Type: application/problem+json
```

Required fields:

- `type`
- `title`
- `status`
- `detail`
- `instance`
- `code`

Stable codes:

- `VALIDATION_ERROR`
- `UNAUTHORIZED`
- `ENDPOINT_NOT_FOUND`
- `EVENT_NOT_FOUND`
- `PAYLOAD_TOO_LARGE`
- `METHOD_NOT_ALLOWED`
- `MALFORMED_REQUEST`

Each category uses a stable, documented URN or URI in `type`.

`detail` must not contain stack traces, Java class names, SQL messages, secrets, public
keys, raw request bodies, or internal exception text.

## Locked public-key design

- Generate exactly 24 random bytes using Java `SecureRandom`.
- Encode with URL-safe Base64 without padding.
- Result: exactly 32 characters matching `[A-Za-z0-9_-]{32}`.
- Store under a database unique constraint.
- Never derive from IDs, names, timestamps, counters, request data, or user input.
- Never log the complete key.
- Return a relative ingestion path; never construct it from an untrusted `Host` header.
- If a rare database collision occurs, retry generation within a small documented bound
  and fail safely if the bound is exhausted.

A 10,000-token generator test verifies format, decoded length, and sample uniqueness.
The test does not claim to statistically prove cryptographic randomness. Cryptographic
suitability is confirmed through code review and an ADR.

## Locked management-token design

From M1-B onward:

- Configuration property is environment-backed.
- Token is required, nonblank, and at least 32 characters.
- The application fails fast at startup when the token is missing, blank, or too short.
- No default token exists.
- `.env.example` contains an empty/commented placeholder and instructions to generate a
  value; it contains no usable secret.
- Test configuration provides a dedicated non-production token.
- Comparison uses a constant-time byte comparison such as `MessageDigest.isEqual`, not
  ordinary string equality.
- Missing or invalid token returns `401 UNAUTHORIZED` using the locked Problem Details
  format.
- The token is never returned or logged.
- This is temporary single-operator protection, not user authentication or
  authorization. Documentation and code comments must say so.

## Locked header and query representation

Headers and query parameters preserve multiple values:

```json
{
  "name": ["value1", "value2"]
}
```

Header behavior:

- normalize header names to lowercase,
- preserve value order when available,
- redact sensitive values before persistence,
- store `[REDACTED]` as the only value for a redacted header name,
- do not retain the raw sensitive values anywhere.

Default exact redaction names:

- `authorization`
- `proxy-authorization`
- `cookie`
- `set-cookie`
- `x-api-key`
- `api-key`
- `x-auth-token`

Additional exact names are configurable and matched case-insensitively after
normalization.

Do not use substring rules such as “contains token,” “contains key,” or “contains
signature.” Signature headers remain visible unless explicitly configured.

Query-parameter names retain their original spelling/casing. Repeated values are
preserved.

## Locked body handling

- Default maximum accepted body size: 1 MiB (1,048,576 bytes).
- Limit is configurable.
- Read at most `configuredLimit + 1` bytes or use an equivalently bounded strategy.
- Do not rely only on `Content-Length`.
- Unknown-length/chunked bodies that exceed the limit must be rejected.
- Exactly the configured limit is accepted.
- One byte over is rejected.
- Rejection returns `413 PAYLOAD_TOO_LARGE`.
- Rejection persists no event or partial event.
- Accepted body bytes are stored exactly in PostgreSQL `bytea`.
- SHA-256 is calculated over those exact bytes and stored as lowercase hexadecimal.
- Body byte length is stored.
- Management detail response returns standard Base64 of the exact bytes.
- Content type is stored separately.

The 1 MiB value is a conservative M1 default, not a permanent provider limit.

## Locked source-IP and timestamp behavior

- Persist the direct socket remote address only.
- Ignore `X-Forwarded-For`, `Forwarded`, and related headers.
- A forged forwarding header must not replace the direct address.
- Trusted-proxy support is a later concern.
- Server generates timestamps as Java `Instant`.
- PostgreSQL stores them as `timestamptz` in UTC.

## Locked logging behavior

M1 must not leak:

- admin-token values,
- full public endpoint keys,
- sensitive header values,
- raw webhook bodies,
- or complete `/hooks/{publicKey}` paths.

Requirements:

- server access logging is disabled by default or sanitizes the public-key path segment,
- Spring request-detail logging remains disabled,
- errors do not log full ingestion URIs,
- request bodies are never logged,
- tests and smoke checks inspect application/access output after successful and failed
  ingestion.

## Locked data model

### `webhook_endpoints`

- `id UUID PRIMARY KEY`
- `name VARCHAR(120) NOT NULL`
- `public_key VARCHAR(32) NOT NULL UNIQUE`
- `created_at TIMESTAMPTZ NOT NULL`

Required listing index:

```text
(created_at DESC, id DESC)
```

### `webhook_events`

- `id UUID PRIMARY KEY`
- `endpoint_id UUID NOT NULL REFERENCES webhook_endpoints(id)`
- `method` with a documented bounded representation
- sanitized multivalue `headers JSONB NOT NULL`
- multivalue `query_parameters JSONB NOT NULL`
- nullable `content_type`
- `body BYTEA NOT NULL`
- `body_size BIGINT NOT NULL` with a nonnegative check
- `body_sha256 CHAR(64) NOT NULL`
- `source_ip` using PostgreSQL `inet` unless an ADR establishes a stronger reason for a
  bounded text representation
- `path` with a documented bounded representation
- `received_at TIMESTAMPTZ NOT NULL`

Required event-listing index:

```text
(endpoint_id, received_at DESC, id DESC)
```

No delete API exists. Flyway must define an explicit non-cascading foreign key behavior;
Codex must not invent cascade deletion.

## Checkpoint structure

M1 is complete only after M1-A through M1-D pass. Codex implements exactly one
checkpoint per execution session.

### M1-A — Repository foundation

Deliverables:

- Java 21 Spring Boot project pinned to the locked platform versions
- Gradle Kotlin DSL and committed Gradle Wrapper
- feature-oriented package skeleton without domain/business implementations
- dependencies needed only for the foundation and already-approved later M1 contracts
- dedicated `integrationTest` source set/task satisfying `docs/testing.md`
- Spotless and Checkstyle satisfying `docs/testing.md`
- application `Dockerfile` with a pinned Java 21 runtime and non-root runtime user
- `compose.yaml` with HookScope and PostgreSQL
- pinned container images, health checks, and readiness/dependency behavior
- Flyway wired and verified against an empty PostgreSQL database without a fake product
  table
- public `/actuator/health`
- Testcontainers integration test against real PostgreSQL
- GitHub Actions running the authoritative full-verification command and preserving useful test reports on failure
- configuration namespace and `.env.example` structure for the future admin token and
  body limit, without enforcement yet
- concise README covering M1-A setup and commands
- all pre-existing source-of-truth documents retained and consistent

Non-goals:

- no endpoint/event entities
- no domain migration
- no `/api/v1/**` management endpoints
- no `/hooks/**` ingestion controller
- no admin-token filter/enforcement
- no Problem Details domain error layer beyond what foundation startup requires
- no later-milestone technology

## Data retention assumption

No expiration or deletion is implemented in M1. Events persist indefinitely. This is a
known limitation documented in M1-D.

## Definition of M1 complete

M1 is complete only when:

- every checkpoint has been implemented and reviewed in order,
- every acceptance row is marked `PASS` by a human based on real evidence,
- the authoritative full-verification command succeeds,
- GitHub Actions succeeds,
- clean-checkout and Compose smoke tests succeed,
- no checkpoint-scoped placeholders or unresolved TODOs remain,
- and documentation matches the actual implementation.
